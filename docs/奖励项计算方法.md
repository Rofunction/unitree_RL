# G1 奖励项计算方法与分析指南

> 用途：拿到一次训练打印输出（`rew_*` + `Mean reward` + `Mean episode length`）后，自己反推每个奖励项的**物理量**和**好坏方向**，判断策略状态。
>
> 适用：`unitree_rl_gym/legged_gym/envs/g1`（基于 legged_gym + IsaacGym + rsl_rl PPO）。

---

## 0. 一句话核心公式

```
rew_X  =  scale_X  ×  ( T_ep / 20 )  ×  ⟨raw_X⟩
```

- `rew_X`：终端打印的 `rew_xxx` 值。
- `scale_X`：写在 `g1_config.py` 里的 `rewards.scales.<name>`（注意正负号）。
- `T_ep`：单个 episode 的实际时长（秒）= `Mean episode length × 0.02`。
- `⟨raw_X⟩`：该奖励项 `_reward_X()` 函数返回值在整段 episode 内的**每步平均原始量**（这才是真正的物理量）。

反推物理量：

```
⟨raw_X⟩ =  rew_X  /  ( scale_X × T_ep / 20 )
```

> 记住这一条，下面所有分析都是它的推论。

---

## 1. 完整计算流水线（从 config 到打印值）

### ① 时间步长 dt

`legged_robot.py:624`

```
dt = decimation × sim.dt = 4 × 0.005 = 0.02   [秒/步]
```

### ② 收集奖励项 + 乘 dt

`legged_robot.py:626` —— `reward_scales = class_to_dict(self.cfg.rewards.scales)`

`class_to_dict` 用的是 `dir(obj)`（`helpers.py:15`），**会把基类继承来的属性一并收进 dict**。所以 G1 的 `scales` 类虽然没写 `torques`，也会继承基类 `legged_robot_config.py:110` 的 `torques = -0.00001`。
→ 这就是为什么打印里会出现 `rew_torques`。

`legged_robot.py:489-495`（`_prepare_reward_function`）：

```
for key in reward_scales:
    if scale == 0:    pop(key)          # scale=0 的项直接丢弃（如 feet_air_time=0, collision=0）
    else:             scale *= dt       # 有效 scale = config_scale × 0.02
```

然后按**约定优于配置**反射注册函数：

```
name = '_reward_' + name
reward_functions.append(getattr(self, name))   # legged_robot.py:503-504
```

→ 这就是为什么 config 里的变量名**必须**正好叫 `feet_contact_forces`：它要能对上方法名 `_reward_feet_contact_forces`（`legged_robot.py:725`）。名字写错 → `getattr` 报错或对不上 → 该项静默失效。

### ③ 每步累加（每项不裁剪）

`legged_robot.py:163-175`（`compute_reward`），每个仿真步：

```
rew = reward_fn() * effective_scale     # = raw × config_scale × dt
rew_buf += rew
episode_sums[name] += rew               # 每项单独累加，且【未裁剪】
if only_positive_rewards:
    rew_buf = clip(rew_buf, min=0)      # 只裁剪【整步总奖励】，不影响 episode_sums
```

关键：`episode_sums[name]` 累加发生在裁剪**之前**，所以打印的 `rew_*` 永远是未裁剪的“真实”分项值。

### ④ 打印（按 episode 归一化）

`legged_robot.py:155`：

```
rew_X = mean(episode_sums_X[本批结束的env]) / max_episode_length_s
```

其中 `max_episode_length_s = episode_length_s = 20`（`legged_robot_config.py:11`，`legged_robot.py:630`），
`max_episode_length = ceil(20/0.02) = 1000 步`（`legged_robot.py:631`）。

### ⑤ 推导主公式

```
episode_sums_X = Σ_steps( raw × config_scale × dt )
               ≈ ⟨raw_X⟩ × num_steps × config_scale × dt
               = ⟨raw_X⟩ × config_scale × (num_steps × dt)
               = ⟨raw_X⟩ × config_scale × T_ep        # T_ep 单位是秒

rew_X = episode_sums_X / 20
      = scale_X × ( T_ep / 20 ) × ⟨raw_X⟩            # 即第 0 节核心公式
```

---

## 2. 三个最重要的结论

### 结论 A：所有 `rew_X` 都随 `T_ep` 等比缩放

因为公式的 `(T_ep/20)` 因子对所有项一视同仁。**机器人一摔倒（episode 变短），所有 `rew_X` 都会按比例变小**，包括正向项。

→ 想看“某个项到底好不好”，必须用反推公式除掉 `(T_ep/20)`，看 `⟨raw_X⟩`，**而不是直接比 `rew_X`**。
→ 比较两次训练（episode 长度不同）时尤其要除掉这个因子，否则会被误导。

### 结论 B：`rew_alive` 是最好的“标尺”

`_reward_alive` 恒返回 `1.0`（`g1_env.py:115-117`），所以：

```
rew_alive = 0.15 × (T_ep / 20)

T_ep              = rew_alive / 0.15 × 20            [秒]
Mean episode len  = rew_alive / 0.15 × 1000          [步]
```

拿到打印，**第一件事**就用 `rew_alive` 估算 episode 长度，去和 `Mean episode length` 交叉验证。

- 健康策略：`rew_alive ≈ 0.15` → ~1000 步（撑满 20s，基本不摔）。
- 崩溃策略：`rew_alive = 0.0087` → ~58 步（起来 1 秒就倒）。✅ 与打印的 `Mean episode length: 55.24` 吻合。

### 结论 C：正负项的“好坏方向”不同

| 类型 | 例子 | scale 符号 | raw 范围 | 好的方向 |
|------|------|-----------|----------|----------|
| 正向目标项 | tracking_lin_vel, tracking_ang_vel, contact, alive | 正 | 有界（见下） | `rew_X` 越接近 `scale` 越好 |
| 负向惩罚项 | lin_vel_z, orientation, torques, dof_acc … | 负 | ≥0（越小越好） | `rew_X` 越接近 0 越好 |

满 episode（T_ep≈20）时的理想 `rew_X`：

| 项 | raw 范围 | 理想 rew（T_ep=20） |
|----|----------|---------------------|
| tracking_lin_vel | [0,1] | ≈ 1.0 |
| tracking_ang_vel | [0,1] | ≈ 0.5 |
| contact | [0,2] | ≈ 0.36（=0.18×2） |
| alive | 恒 1.0 | ≈ 0.15 |

## 3. `only_positive_rewards` 裁剪的微妙之处（容易误判）

`only_positive_rewards = True`（`legged_robot_config.py:120`）：每步把**整步总奖励** clip 到 ≥0。

- 影响的是**学习信号**：当某一步所有项加起来是负的，这一步对策略梯度贡献为 0（被抹平）。
- **不影响**打印的 `rew_*`：分项值在裁剪前就累加进 `episode_sums` 了。

后果：一个看起来“很大”的负惩罚（如 `rew_feet_contact_forces = -0.266`）可能在很多步里其实被整步裁剪抹掉了，对学习的实际惩罚力度比日志显示的要小。判断某个惩罚“够不够”，要结合**趋势**（值在下降→生效；长期不动→可能被裁剪/太弱），而不是只看绝对值。

## 4. G1 当前全部活跃奖励项（逐项说明）

> 阈值/目标常量（`g1_config.py:90-93`）：`base_height_target = 0.78`，`max_contact_force = 150`，`tracking_sigma = 0.25`（`legged_robot_config.py:121`）。
> 被丢弃的零 scale 项：`termination, feet_air_time, collision, feet_stumble, stand_still`。
> ⚠️ 注意 `torques = -1e-5` 是从基类**继承**来的，不在 g1_config.py 里，但是活跃项。

### 4.1 正向目标项（越大越好，有上界）

#### tracking_lin_vel — `scale = 1.0`
`legged_robot.py:693-696`
```
lin_vel_error = ‖cmd_xy − base_lin_vel_xy‖²
raw = exp( − lin_vel_error / 0.25 )          # ∈ [0,1]
```
- 物理量：xy 速度跟踪的高斯核。`raw→1` 表示完全跟上指令速度。
- 健康值 `raw≈0.83`（rew≈0.816）→ 速度跟踪不错。
- 注意是 `/sigma` 不是 `/sigma²`，sigma=0.25 较严，速度误差 ~0.2 m/s 就把 raw 压到 ~0.85。

#### tracking_ang_vel — `scale = 0.5`
`legged_robot.py:698-701`
```
raw = exp( − (cmd_yaw − base_ang_vel_z)² / 0.25 )    # ∈ [0,1]
```
- 物理量：yaw 角速度跟踪。
- 你表里 `raw≈0.49`（rew≈0.243）→ **偏弱**，转向跟踪不太好，是可改进项。

#### alive — `scale = 0.15`
`g1_env.py:115-117`，`raw ≡ 1.0`。用途见结论 B（标尺）。

#### contact — `scale = 0.18`（步态相位接触奖励）
`g1_env.py:100-107`
```
对每只脚 i:
  is_stance = leg_phase[i] < 0.55        # 该脚应在站立相
  contact   = contact_force_z[i] > 1     # 实际是否接触
  res += ~(contact XOR is_stance)        # 相位与接触一致则 +1
raw = Σ_i ...  ∈ [0, 2]                   # 两只脚
```
- 物理量：步态节奏正确性（支撑相有接触、摆动相无接触）。
- `raw≈1.72/2`（rew≈0.309）→ 节奏好，接近理想 0.36。

### 4.2 负向惩罚项（raw≥0，越小越好）

#### lin_vel_z — `scale = −2.0`
`legged_robot.py:637-639`
```
raw = (base_lin_vel_z)²                   # 即 vz²
```
- 物理量：身体上下颠簸。
- 反推 `|vz| = √⟨raw⟩`。你表里 ⟨raw⟩≈0.02 → rms `|vz|≈0.14 m/s`，挺平稳。

#### ang_vel_xy — `scale = −0.05`
`legged_robot.py:641-643`
```
raw = ωx² + ωy²                           # roll/pitch 角速度平方和
```
- 物理量：身体 roll/pitch 晃动。反推 `rms(ωxy)=√⟨raw⟩`。你表里 ≈0.83 rad/s。

#### orientation — `scale = −1.0`
`legged_robot.py:645-647`
```
raw = gx² + gy²                           # 重力在身体坐标系的水平投影
```
- 物理量：身体倾角。因 `gx²+gy²+gz²=1`，`raw ≈ sin²(倾角)`。
- 反推 `倾角 ≈ arcsin(√⟨raw⟩)`。你表里 ⟨raw⟩≈0.0038 → 倾角≈3.5°，很正。

#### base_height — `scale = −10.0`
`legged_robot.py:649-652`
```
raw = (root_z − 0.78)²
```
- 物理量：躯干高度偏离目标 0.78m。scale 很大（−10），是强约束。
- 反推 `|高度偏差| = √⟨raw⟩`。

#### torques — `scale = −0.00001`（**继承自基类**）
`legged_robot.py:654-656`
```
raw = Σ_i τ_i²                            # 所有关节力矩平方和
```
- 物理量：能耗/力矩。scale 极小，主要是正则项。

#### dof_vel — `scale = −1e-3`
`legged_robot.py:658-660`
```
raw = Σ_i q̇_i²                            # 关节速度平方和
```

#### dof_acc — `scale = −2.5e-7`
`legged_robot.py:662-664`
```
raw = Σ_i ( (last_dof_vel − dof_vel) / dt )²     # 有限差分估计的关节加速度平方和
```
- 注意：是**有限差分**算出的加速度（单位 rad/s²），不是真实传感器加速度。

#### action_rate — `scale = −0.01`
`legged_robot.py:666-668`
```
raw = Σ_i (a_t − a_{t-1})²                # 相邻动作变化平方和
```
- 物理量：动作抖动，鼓励平滑。

#### dof_pos_limits — `scale = −5.0`
`legged_robot.py:678-682`
```
out_of_limits = -(dof_pos − lower).clip(max=0) + (dof_pos − upper).clip(min=0)
raw = Σ_i out_of_limits_i                 # 超出关节硬限位的量
```
- 物理量：关节撞限位的程度。正常为 0，只有撞限位才 >0。scale 很大（−5），是硬约束。
- 健康策略应接近 0；持续非 0 说明关节在硬蹭限位。

#### feet_contact_forces — `scale = −1e-3`（你新加的）
`legged_robot.py:725-727`
```
raw = Σ_i max(0, |F_foot_i| − 150)        # 超过 150N 的接触力才罚
```
- 物理量：脚底“过量”接触力（跺脚）。`max_contact_force=150` 是阈值。
- 阈值含义：单脚承重（G1 约 35kg，单脚静载 ~170–350N）——**150N 偏低，可能连正常承重都罚**。判断这个惩罚是否在罚“正常承重”而非“跺脚冲击峰值”，看 `⟨raw⟩` 是否长期居高不下。
- ⚠️ 若阈值太低，惩罚梯度会逼策略“不敢压实”→ 支撑不稳 → 步态塌掉（上轮崩溃的嫌疑机制之一）。

#### feet_swing_height — `scale = −5.0`
`g1_env.py:109-113`
```
contact = |F_foot| > 1
raw = Σ_i (foot_z_i − 0.08)² × ~contact   # 摆动相脚抬得不够 0.08m 就罚
```

#### contact_no_vel — `scale = −0.2`
`g1_env.py:119-124`
```
raw = Σ_i ( 接触时的脚速度 )²              # 接触地面时脚还在滑就罚
```
- 物理量：足端打滑。

#### hip_pos — `scale = −1.0`
`g1_env.py:126-127`
```
raw = dof_pos[:,1]² + dof_pos[:,2]² + dof_pos[:,7]² + dof_pos[:,8]²
    # 左右髋 roll/pitch 关节角度平方和
```
- 物理量：髋部 roll/pitch 偏离中立位的程度，鼓励双腿收拢、不外撇。

## 6. 分析 checklist（拿到一次打印怎么做）

1. **先看长度**：`Mean episode length` 与 `rew_alive/0.15×1000` 是否一致？算出 `T_ep` 和 `T_ep/20`。
   - < 200 步（<4s）→ 机器人在摔，所有 `rew_X` 都会被压小，**先别急着比分项**。
2. **看正向目标项的 `⟨raw⟩`**（除掉 `T_ep/20`）：
   - tracking_lin_vel、tracking_ang_vel 是否接近 1？
   - contact 是否接近 2？
3. **看惩罚项的 `⟨raw⟩`** 是否在下降：
   - 重点 dof_pos_limits、feet_contact_forces、feet_swing_height、contact_no_vel —— 这些直接关系步态质量。
4. **跨 run 比较**：务必用 `⟨raw⟩` 比，不要直接比 `rew_X`（不同 episode 长度不可比）。
5. **判断你新加的 feet_contact_forces**：
   - 阈值 150N 是否在罚正常承重（`⟨raw⟩` 长期高且不降）？
   - 趋势：`⟨raw⟩` 下降→生效；不动→可能太弱或被整步裁剪（见第 3 节）。

### 附：为什么改 reward scale 后 `--resume` 安全但可能训崩

- `--resume` 只恢复 actor/critic 权重 + 优化器 + 归一化统计量（`task_registry.py:125` `runner.load`），**不**恢复奖励函数；环境从当前 `cfg` 重建（`task_registry.py:68`）。
- 改 reward scale **不改网络维度**（obs=47, action=12 不变）→ 架构兼容，能正常加载。
- 但奖励景观变了，已加载的策略处在“陌生”的奖励地形里，critic 预测也失准，PPO 可能做出坏更新 → 若更新太激进就会像上轮那样塌成“起来就倒”。
- 续训要小步改（一次别动太多项 / 先小 scale），并保留崩溃前的 checkpoint 以便回滚（每次续训是独立时间戳目录，不会覆盖旧 run）。
